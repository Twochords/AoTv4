# Fellowship window — client install

Roster, persistent cross-zone chat, and a campfire your fellowship can travel to.

## Files

1. Copy **`uifiles_default/EQUI_AoTFellowshipWnd.xml`** into `<EQ>\uifiles\default\`.
2. Add this line to `<EQ>\uifiles\default\EQUI.xml`, beside the other AoT includes:

   ```xml
   <Include>EQUI_AoTFellowshipWnd.xml</Include>
   ```

3. Rebuild `dinput8.dll` (`eq-core-dll-vs2022.vcxproj`, toolset v143) and copy it next to `eqgame.exe`.
4. Copy the regenerated **`spells_us.txt`** and **`dbstr_us.txt`** so the campfire spell renders by
   name instead of "Unknown Spell".

⚠️ **Missing either of the first two and `CCustomWnd` silently returns** — no window, no error. The
dll writes `<EQ>\aotv4_fellowship.log`; a `pXWnd=NULL` line there means exactly this.

## Opening it

- **AoT menu → Fellowship** (the launcher grew 322 → 352 tall for the new button)
- `/fellowship`, or `/fship`

## ⚠️⚠️ This is NOT the client's own fellowship window, and that one cannot be used

The client has one — `pinstCFellowshipWnd` is mapped at `0xF712AC` — but server side
`OP_FellowshipUpdate` is **a name in `emu_oplist.h` and nothing else**: no handler in
`client_packet.cpp`, no struct in `eq_packet_structs.h`, and **no mapping in the RoF2 patch**, so it
has no wire opcode for this client. Forcing it open shows an empty panel forever, and populating it
would mean reverse-engineering both the opcode number and the packet format with no reference.
CLAUDE.md §13 records the same dead end for the native trader window — which had *more* to work with
(a mapped opcode and a real activation path) and was still abandoned.

📌 **So the look is copied instead of the plumbing.** `EQUI_AoTFellowshipWnd.xml` is generated by
transforming the client's own `EQUI_FellowshipWnd.xml`: every coordinate, size and template is byte
for byte the native window's, with the screen renamed `AoTFellowshipWnd` and every piece prefixed
`AFW_` so it cannot collide. It is identical rather than similar because it is the same layout.

## What the buttons do

| Button | Sends |
|---|---|
| Create | `fshipform <MOTD box text>` — the box doubles as the name field before you have a fellowship |
| Invite | `fshipinv <box text>` — **blank means your current target**, as the native window does |
| _(the invitee answers)_ | `fshipaccept` / `fshipdecline`, from saylinks in their chat |
| Remove / Make Leader | `fshipkick` / `fshipleader` on the selected roster row |
| Leave / End Fellowship | `fshipleave` / `fshipend` |
| Update (MOTD) | `fshipmotd <text>` — leader only |
| Refresh List | `fshipreq` |
| Create Camp | `fshiplight <selected kind>` |
| Destroy Camp | `fshipdouse` |
| Travel | `fshipgo` — **not a native button**, see below |

⚠️ **Toggle XP and Show All Possible are hidden**, not disabled. XP sharing was declined by the
design and there is nothing to filter with three fires — and §16 records that a button which looks
live and silently does nothing reads as a broken window. Hidden rather than greyed because this
build maps no reliable enable setter (`EQClasses.h` only *declares* `CXWnd::IsEnabled`, and writing a
raw member offset is §13's crash); `Show` **is** mapped.

## Notes

- ⚠️ The dll validates **nothing**. The 12 cap, leader-only actions and the four travel gates
  (region unlocked, not in combat, not in an instance, cooldown) are all re-checked server side, so
  a modified client pressing a button gains only a refusal in chat.
- 📌 **Online/zone per member is stamped, not queried.** There is no `is_online` binding and no
  cross-zone location call, so each member's own client stamps `fship_at_<charid>` every 30 s and
  anything older than 90 s reads offline. Without that the roster could only ever report members
  standing in the viewer's own zone.
## ⚠️⚠️ There is no summon — each member travels themselves

Nothing here pulls another player to a campfire, and that matches live: a fellowship campfire is a
**destination**, not a summon. Three ways to reach one, all doing the same thing:

| | |
|---|---|
| **Fellowship Insignia** (item 147975) | click it from your bags — the live-style route |
| **Travel** button on the Camp tab | `AFW_TravelToCamp` |
| `/say fshipgo`, or the Fellowmaster's saylink | the no-dll fallback |

⚠️⚠️ **The insignia is the ONE permanent item in this feature, and it is only safe because
`death_loss.M.is_kept` exempts it.** Everything else the fellowship hands out is a consumable for a
reason: the roguelite wipe destroys anything outside that list, which is how the tradeskill tools
were permanently lost (§32). An insignia was deliberately **not** built until the exemption existed.
Remove that line and the first death silently cuts a character off from campfires forever.
📌 Denara re-hands one on hail when you have none, which is the recovery path either way. It is Lore,
so it cannot be stockpiled.

⚠️ The native Camp tab has **no** Travel button — live puts travel on the item — so
**`AFW_TravelToCamp` is an added piece**, the one place this window is not byte-for-byte the native
layout.

- ⚠️⚠️ **An invite is an OFFER, and the answer arrives as saylinks in chat, not as a dialog.** There
  is no native invite popup to drive — `OP_FellowshipUpdate` has no wire opcode here — so the
  invitee gets `[ Accept ]` / `[ Decline ]` links and has 120 seconds to use one. Every gate is
  re-tested at the moment they answer, because a fellowship can be disbanded or filled in between.
- ⚠️ **The roster's seven columns are assigned by POSITION** — `name|leader|level|class|zone|online|laston`
  — and neither side names the fields. Adding one server side without updating
  `core_fellowship.cpp` shifts every column to its right, which is how "offline" once rendered under
  **Class**. `XP Sharing` is deliberately left blank: the feature does not exist here, and the column
  survives only because this layout is the native one byte for byte.
- The window is driven entirely by chat (`FSHIPDATA` / `FSHIPFIRE` / `FSHIPMOTD` out, `/say fship*`
  in), all of it swallowed by the dll, exactly like every other AoTv4 window.
